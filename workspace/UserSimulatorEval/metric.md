# 用户模拟器类人性评测指标

评测单位是一条已配对的交互：`初始问题 → 客服澄清问题 → 用户回复`。同一测试集需要同时保留
真实用户回复与用户模拟器生成的回复；两者交给相同的 Judge 标注，再由脚本在本地做汇总。

## 指标

1. **信息提供效率**：每条用户回复中独立信息点的平均数量。

   信息点是可独立识别、可能有助于处理问题的事实、属性、地点、时间、设备、症状、选择或状态；
   同一事实只计一次。礼貌用语、纯情绪和无意义重复不计入信息点。

2. **信息泄漏率**：包含至少一条“客服本次没有明确、准确追问”的信息点的回复占比。

   对每个信息点，Judge 标记 `requested_by_agent`。只有客服本次问题明确索取该信息点时才为
   `true`；用户主动补充、仅宽泛相关或客服没有问到的信息均为 `false`。一条回复只要有任一
   `false` 信息点，就计为一次信息泄漏。

3. **回复长度**：用户回复的平均可见字符数，忽略空白字符。

   使用字符而不是 tokenizer token，避免不同模型、不同 tokenizer 导致数值不可比。

4. **不回复率**：用户没有回应客服澄清问题、而只是重申或改述初始需求的回复占比。

   仅当回复为空，或明显完全无视追问且只强调原始需求时，才记为“不回复”。“不知道”“不清楚”、
   “没有”、是/否回答、部分回答、纠正客服前提，都属于对追问作出了回应，**不**计为不回复。

## 解释与比较

这四个指标描述回复行为，不应被合成为未经验证的单一“类人分数”。评测应报告真实用户与模拟器的
并列数值及 `模拟器 − 真实用户` 差值：

- 信息提供效率、回复长度接近真实用户，通常表示回复粒度相近；但不是越大越好；
- 信息泄漏率和不回复率应与真实用户分布接近，不能机械追求零；
- 所有 Judge 标注、逐条信息点与理由都应随评测结果落盘，以便人工审计。
